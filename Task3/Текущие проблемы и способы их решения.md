## Анализ проблем и рисков

В текущей архитектуре системы InsureTech есть несколько потенциальных проблем, которые могут усугубиться с ростом нагрузки и увеличением числа страховых компаний.

### 1. Проблемы синхронных вызовов API

- Сервис ins-product-aggregator делает последовательные запросы ко всем страховым компаниям, агрегируя результаты в одном синхронном вызове.
- Если хотя бы один из поставщиков отвечает с задержкой, это влияет на общее время ответа сервиса, замедляя обработку запроса.
- В случае ошибки взаимодействия с одной из страховых компаний возможна частичная потеря данных.

**Риски:**

- Увеличение количества страховых компаний пропорционально увеличит среднее время ответа и вероятность ошибок.
- Высокая зависимость от доступности внешних API.

### 2. Проблемы репликации данных в сервисах core-app и ins-comp-settlement

- core-app и ins-comp-settlement хранят локальные копии данных о продуктах, но их обновление происходит раз в 15 минут и раз в сутки соответственно.
- Данные могут устаревать, что приводит к расхождению информации между сервисами и реальными тарифами страховых компаний.
- Ошибки или задержки в API ins-product-aggregator могут приводить к неполучению свежих данных.

**Риски:**

- Неполнота данных.
- Возможность продажи устаревших продуктов клиентам.

### 3. Проблема взаимодействия ins-comp-settlement с core-app

- Запрос всех оформленных страховок за день по REST API приводит к высокой нагрузке на core-app, так как данные за сутки могут быть объёмными.
- В случае сбоя запроса ins-comp-settlement должен будет повторить запрос, что создаёт дополнительную нагрузку.

**Риски:**

- Возможные сбои в ночных обработках ins-comp-settlement.
- Повышенная нагрузка на core-app.

---

## Предлагаемые решения

1. Перевести взаимодействие ins-product-aggregator со страховыми компаниями в асинхронный режим.
    - Использовать топики Kafka для распространения изменений тарифов.
2. Заменить периодическое обновление данных в core-app и ins-comp-settlement на подписку через Event-Streaming.
    - Вместо опроса раз в 15 минут/сутки, сервисы будут получать обновления сразу при получении данных в ins-product-aggregator.
3. Использовать паттерн Transactional Outbox в core-app.
    - Гарантирует, что события о новых страховках не теряются при сбоях.
4. Перевести обмен данными между core-app и ins-comp-settlement на Event-Streaming.
    - Добавить Debezium для отслеживания лога транзакций таблицы с событиями об оформленных страховках.
    - Debezium публикует событие о новой оформленной страховке, ins-comp-settlement подписывается на эти события.
